# AR Soda Cans

Point a phone camera at a soda can; a 3D can locks onto the real one and an info
card shows what you're looking at.

Image tracking runs entirely in the browser — no WebXR, so it works on iOS
Safari as well as Android Chrome.

| | |
|---|---|
| Tracking | [MindAR](https://github.com/hiukim/mind-ar-js) image targets (WASM + tfjs) |
| Rendering | Three.js, procedural can — no 3D asset files |
| App | Vite + React + TypeScript |

## Quick start

```bash
npm install
npm run compile:targets   # builds public/targets.mind from public/targets/*.jpg
npm run dev
```

`npm run dev` prints two addresses. Use the **Network** one on your phone:

```
➜  Local:   https://localhost:5180/      <- laptop only
➜  Network: https://192.168.1.122:5180/  <- the phone needs THIS
```

> `localhost` means "this device", so it will not resolve from the phone. Always
> use the Network address there. Same Wi-Fi, and accept the certificate warning
> once (iOS Safari: Show Details → visit this website; Android Chrome: Advanced →
> Proceed) — it stays a secure context afterwards, so the camera works.

Allow the camera, then point it at a registered can. On a fresh clone that means
one of the placeholder labels in `public/targets/`, shown on a screen or printed.

## Testing on your phone

### 1. Try what is already compiled

Open the **Network** address, allow the camera, and point it at the can. Rotate
it slowly through a full turn.

| What you see | What it means |
|---|---|
| The 3D can appears and holds through the rotation | Done — nothing else needed |
| It flickers, or only catches at some rotations | Targets are too weak → step 2 |
| Nothing at all, ever | Not target quality — check the registry and that `npm run compile:targets` ran after your last edit |

### 2. Reshoot with the phone if step 1 disappoints

Open **`/dev/capture.html` on the Network address** — again, not `localhost`:

```
https://<your-lan-ip>:5180/dev/capture.html
```

Fill in the drink's details, tap **Start capture**, then shoot 6 angles rotating
the can ~60° between shots. Each shot crops to the on-screen guide and lands in
`public/targets/`; at the end it prints a registry entry to paste.

Real photos carry the actual lighting, specular highlights and camera
characteristics MindAR meets at runtime, so they beat generated targets
comfortably. See [Adding a real can](#adding-a-real-can).

> If a can already has generated slices registered, **remove them when you add
> real photos**. Otherwise you compile both sets — twice the targets, twice the
> wait, for targets you no longer use.

### First run: mkcert needs your password

`npm run dev` serves over HTTPS because `getUserMedia` refuses to run on a plain
`http://` LAN address. The first start installs a local certificate authority
and needs sudo:

```bash
~/.vite-plugin-mkcert/mkcert -install
```

Run that once in your own terminal, then `npm run dev` works from then on. To
skip HTTPS entirely (desktop-only testing — `localhost` is already a secure
context):

```bash
NO_HTTPS=1 npm run dev
```

## The placeholder labels are not real cans

`public/targets/placeholder-*.jpg` are **invented labels** generated by
`npm run targets:placeholders`. They are not photographs of real cans and not
real brands. They exist so the app runs on a fresh clone, and they are
deliberately feature-dense because that is what tracks well.

## Adding a real can

**MindAR is a planar tracker and a can is a cylinder.** One photo only matches
while the can is turned roughly as it was photographed, so each can carries
several photos taken around it — all of them mapping back to the same drink.

Two things worth knowing before you start:

- Targets are **per artwork, not per object**. Register the Coke label once and
  every can with that artwork works. Coke Zero, Diet, 500ml and seasonal designs
  are different artwork and need their own entries.
- Photograph the **real can**, never a flat label graphic off the web. At runtime
  MindAR sees a curved, shaded label, and targets shot under the same conditions
  match far better.

### 1. Capture

```bash
npm run dev
```

Open **`/dev/capture.html` on the phone that will run the AR**. Fill in the
drink's details, then shoot 6 angles, rotating the can ~60° between shots. Each
shot is cropped to the on-screen guide and written straight into
`public/targets/`, so there is nothing to transfer and nothing to crop.

Fill the guide with the printed label. Leave out the metal top, the background,
and the curved edges where the label falls away.

### 2. Register

The capture page prints a ready-to-paste entry. Add it at the **end** of `cans`
in `src/data/cans.ts`:

```ts
{
  id: 'coca-cola',
  targetImages: [
    'coca-cola-01.jpg',
    'coca-cola-02.jpg',
    // ...
  ],
  name: 'Coca-Cola',
  flavour: 'Original cola',
  calories: 139,
  volumeMl: 330,
  bodyColor: '#c8102e',
  scale: 1
}
```

### 3. Compile

```bash
npm run targets:check    # optional sanity check, seconds
npm run compile:targets  # ~1-2 min per photo
```

> **The MindAR target index is the index into the flattened photo list.**
> Reordering `cans`, or reordering a can's `targetImages`, without recompiling
> silently pairs cans with the wrong 3D model. Always append, always recompile.
> `npm test` checks this.

### Label texture

The first photo doubles as the texture wrapped around the 3D can. Because a
flat-on photo only shows about half the circumference, it is mapped across 180°
and mirrored round the back.

If you have a proper flat 360° unwrap of the label, point `labelTexture` at it —
that switches the mapping to a single 1× wrap, which is what an unwrap needs.
Getting this wrong shows the label twice.

`scale` is the model's height as a multiple of the target image's width. Tune it
by eye for photographed targets. For slices generated by `targets:from-wrap` it
is computed for you (115/66 = 1.74, since a slice is exactly one can diameter
wide).

## Generating targets from label artwork

If you have a flat 360° label unwrap, you can generate targets without
photographing anything:

```bash
npm run targets:from-wrap public/targets/coca-cola-wrapper.jpg coca-cola
npm run targets:from-wrap <wrapper> <id> --slices 12
```

**The flat unwrap itself is not a usable target** — measured, it scores 0-10
matches against a rendered can, which is noise. MindAR matches by planar
homography, and a flat full wrap has no planar correspondence to a curved
surface. So the script pre-warps the artwork the way a cylinder distorts it
(a surface point at angle θ appears at `x = R·sin(θ)`) and emits one slice per
rotation, 30° apart by default. Shading is baked in because it measures better.

That 30° spacing comes from measurement: a slice matches its own rotation
strongly, holds to about 15-20°, and is gone by 30°.

**This route is unproven against real cans.** Every one of those numbers came
from matching against a synthetic render of the same artwork using a smooth
cosine shading model. Real aluminium has specular highlights and environment
reflections the model does not reproduce, and vector artwork is not a
photograph. Treat it as a free first attempt, not a substitute for photos.

It also needs high-resolution artwork. A wrapper only ~700px wide covers the
whole circumference, so every slice is upsampled and soft.

### Checking a photo before compiling

`npm run targets:check [file...]` runs MindAR's own matcher against a squeezed
copy of the image and reports the widest simulated viewing angle that still
matches.

Read the output carefully: it is an **upper bound**. Matching an image against a
clean synthetic warp of itself is the easiest possible test — a real camera adds
blur, compression, glare and uneven light, and a real can adds cylindrical
distortion that a horizontal squeeze only approximates. A pass means "not
degenerate", not "will track well". A **failure is conclusive**, though: an image
that cannot match a clean copy of itself has no chance against a camera.

Only the phone tells you whether a target really tracks.

## Testing without a phone or a can

```bash
NO_HTTPS=1 npm run dev
# http://localhost:5180/dev/smoke.html   (localhost is fine here — laptop only)
```

`dev/smoke.ts` replaces `getUserMedia` with a canvas stream rendering a target
image, so MindAR gets a "camera" it can genuinely detect against. From the
console:

```js
smoke.active        // id of the tracked can, or null
smoke.show(1)       // point the fake camera at cans[1]
smoke.hide()        // point it at nothing, to exercise target-lost
smoke.stop()        // tear the scene down
smoke.startAnother()// second scene in the same container, to check that
                    // stopping one never removes the other's video
```

Running two scenes at once is heavy — it can wedge the renderer on some
machines. Use `startAnother()` deliberately, not casually.

Note that a browser-automated tab often does not run `requestAnimationFrame`, so
the 3D render loop may be idle there even though tracking works. Verify visuals
on a real device.

## Scripts

| | |
|---|---|
| `npm run dev` | HTTPS dev server on the LAN |
| `npm run build` | typecheck + production build |
| `npm run typecheck` | `tsc --noEmit` |
| `npm test` | Vitest |
| `npm run storybook` | component workbench (info card) |
| `npm run compile:targets` | `public/targets/*` → `public/targets.mind` |
| `npm run targets:check` | predict how well photos will track (upper bound) |
| `npm run targets:from-wrap` | generate targets from a flat 360° label unwrap |
| `npm run targets:placeholders` | regenerate the placeholder labels |

`npm test` includes a **project setup** block that fails if a registered can has
no photo on disk or `targets.mind` is missing. That is a setup signal, not a
code failure.

## Layout

```
public/targets/        tracking photos, also used as can label textures
public/targets.mind    compiled feature data (generated, committed)
scripts/               target compiler + placeholder generator
src/data/cans.ts       the drink registry — target index is the array index
src/ar/arScene.ts      MindAR + three lifecycle, owns the camera and webgl
src/ar/buildCan.ts     procedural can mesh
src/ar/useArScene.ts   react bridge
src/components/        camera gate, ar overlay, info card
dev/smoke.*            desktop AR harness with a fake camera
dev/capture.*          phone capture page for shooting target photos
```

## Upstream workarounds

`mind-ar@1.2.5` predates several browser and three.js changes. Each of these is
load-bearing — removing one produces a black screen or a crash:

- **`sRGBEncoding`** was removed from three in r152. A small Vite transform in
  `vite.config.ts` drops the dead import rather than pinning three to 2023.
- **Autoplay.** MindAR sets the video's `muted` *attribute*, which sets
  `defaultMuted` but not the `muted` property on a dynamically created element,
  so browsers block autoplay and the feed never starts. `arScene.ts` mutes the
  element the moment it is inserted.
- **`z-index: -2`** on MindAR's video puts it behind the nearest stacking
  context, where an opaque page background covers it. `.ar-view__stage` sets
  `isolation: isolate`.
- **The resize listener** MindAR binds in its constructor dereferences a
  controller that only exists between `start()` and `stop()`, and is never
  removed. `arScene.ts` captures it at construction and manages it itself.

## Known limits

- One can tracked at a time (`maxTrack: 1`) so the info card is unambiguous.
- Compile cost and `targets.mind` size scale with the TOTAL number of photos,
  not the number of cans: 6 angles × 3 cans is 18 targets, ~450kB and a minute
  or two each. Compilation is CPU-bound and single-threaded.
- `targets.mind` is fetched up front, so it is a real page-weight cost.
- The bundle is ~2MB (560kB gzipped), dominated by tfjs.
- The capture endpoint writes files from an unauthenticated dev-server route. It
  is mounted only for `vite dev` — never build or preview — writes to a fixed
  directory, rejects any id outside `[a-z0-9-]`, and checks JPEG magic bytes.
